## 1. 서비스 한 줄 요약

관광객은 **성향 테스트 → 위치 선택 → AI가 짜준 데이트·관광 코스 → 방문 후 평가**를 하고,
상권 주인은 **빅데이터와 관광객 평가를 합친 객관적인 "상권 건강 지표"와 AI 개선 제안**을 받습니다.
관광객의 평가는 다시 상권 지표와 추천 품질로 돌아가는 **순환 구조**가 핵심입니다.

```
 [관광객]  성향 테스트 ─▶ 코스 추천 ─▶ 방문 ─▶ 평가·리뷰
                ▲                                    │
                │          추천 가중치 갱신          ▼
           ┌────┴────────────────────────────────────────┐
           │  제주 빅데이터 (소비·유동인구·관광·교통·날씨) │
           │        + 앱 내 평가 데이터 (자체 생성)       │
           └────┬────────────────────────────────────────┘
                │          상권 지표 산출
                ▼
 [상권 주인]  상권 건강 지표 ─▶ 경쟁·고객 분석 ─▶ AI 개선 제안
```

## 2. 대회 조건과 대응 방안

| 대회 조건 (claude.md) | 대응 방안 |
|---|---|
| 제주빅데이터센터 또는 제주데이터허브 데이터 1종 이상 활용 | 공개 데이터 + 센터 방문 데이터를 **6종 이상** 결합 (3장) |
| 주제에 맞는 AI Agent 구현 | 관광객용·상권용 Agent와 이를 조율하는 오케스트레이터로 구성된 멀티 Agent (5장) |
| 제주시 내 PC에서 동작 | 전체 스택을 **단일 PC 로컬 실행**으로 설계. Docker Compose 한 번으로 기동 |
| 센터·허브 데이터의 외부 유출 금지 | **로컬 LLM** 사용 (외부 LLM API로 원천 데이터 전송 없음), DB·벡터 DB 모두 로컬, 지도는 오프라인 타일 우선 (6장) |
| 복합적이고 실용적이며 완성도 있는 서비스 | 양면(관광객·상권) 사용자, 평가 피드백 루프, 실제 화면 동작 데모까지 구현 |

## 3. 활용 데이터 계획

### 3.1 외부 데이터 (제주데이터허브·제주빅데이터센터) `[확인 필요: 실제 데이터명·기간·단위]`

| # | 데이터 (후보) | 출처 | 주요 활용 | 사용처 |
|---|---|---|---|---|
| D1 | 업종·지역별 카드 소비 데이터 (내국인/외국인, 시간대, 성별·연령) | 빅데이터센터 / 데이터허브 | 상권 매출 추세, 방문객 구성, 시간대별 활성도 | 상권 지표, 코스 시간 배치 |
| D2 | 유동인구 데이터 (격자·행정동 단위, 시간대) | 빅데이터센터 | 혼잡도, 유동 대비 매출 전환율 | 상권 지표, 혼잡 회피 추천 |
| D3 | 내비게이션 목적지 검색·도착 데이터 | 데이터허브 | 장소 인기도, 관광객 이동 패턴 (A 다음 B) | 코스 연결 확률, 인기 추세 |
| D4 | 관광지 방문객·입장객 통계 | 데이터허브 | 관광지 수요, 계절성 | 코스 후보, 계절 보정 |
| D5 | 상가(상권) 정보 · 음식점/카페 인허가 데이터 | 데이터허브 / 공공데이터 | 점포 위치·업종·개폐업 | 경쟁 밀도, 상권 생존 지표 |
| D6 | 대중교통(버스 정류장·승하차) 및 주차장 | 데이터허브 | 접근성 점수 | 코스 이동수단·접근성 |
| D7 | 기상 데이터 (강수·풍속·기온) | 데이터허브 / 기상청 | 날씨 연동 실내외 코스 전환 | 코스 추천 |
| D8 | 관광 SNS·리뷰 키워드 데이터 | 데이터허브 `[있으면]` | 장소별 분위기 태그 (감성, 오션뷰 등) | 성향-장소 매칭 |

> 최소 요건은 1종이지만, 심사의 "복합성"을 위해 **D1·D2·D3·D5는 필수**, 나머지는 확보되는 만큼 추가합니다.

### 3.2 자체 생성 데이터

| 데이터 | 설명 |
|---|---|
| 성향 프로필 | 성향 테스트 결과 (4축 점수, 유형) |
| 코스 로그 | 추천된 코스, 실제 선택·방문한 장소 |
| 평가·리뷰 | 장소별 별점, 항목별 평가 (맛·분위기·가격·친절·혼잡), 자유 리뷰 |
| 상권 등록 정보 | 사장님이 등록한 매장 정보·메뉴·이벤트 |

### 3.3 데이터 결합 키

- **공간**: 위경도 → 격자(예: 100m 또는 데이터 기본 격자) · 행정동으로 통일
- **시간**: 연-월-요일-시간대로 통일
- **업종**: 카드 업종 코드 ↔ 상가 업종 코드 매핑 테이블 직접 구축

## 4. 핵심 기능

### 4.1 관광객 기능

**(1) 데이트·여행 성향 테스트**
- 12문항 내외, 4개 축으로 점수화 → 16유형 (예: "노을 감성 탐험가")

| 축 | 양 끝 |
|---|---|
| 활동성 | 액티비티 ↔ 힐링 |
| 공간 | 자연·바다 ↔ 도심·핫플 |
| 취향 | 미식 중심 ↔ 풍경·사진 중심 |
| 스타일 | 계획형 ↔ 즉흥형 (코스 촘촘함·여유 시간 조절) |

- 동행 정보(연인/친구/가족), 예산, 이동수단(렌터카/대중교통), 이용 시간을 추가 입력

**(2) 위치 기반 코스 추천**
- 지도에서 위치 클릭 또는 현재 위치 사용
- Agent가 3~5곳의 코스를 시간표 형태로 제안 (예: 15:00 카페 → 16:30 해안 산책 → 18:00 노을 명소 → 19:00 저녁)
- 각 장소마다 **추천 이유**를 데이터 근거와 함께 표시
  - "이 시간대 2030 커플 방문 비중이 높은 곳 (카드 소비)"
  - "현재 시간 혼잡도 낮음 (유동인구)"
  - "이 관광지 다음에 많이 가는 곳 (내비게이션)"
- 날씨가 나쁘면 실내 대안 코스로 자동 전환
- 대화로 수정: "저녁은 해산물로 바꿔줘", "1곳 줄여줘"

**(3) 방문 후 평가**
- 장소별 별점 + 항목 평가 + 한 줄 리뷰
- 위치·시간 기반 **방문 인증** (코스에 포함되고, 해당 시간대에 반경 내 있었을 때만 평가 가능) → 허위 리뷰 방지
- 평가 결과는 성향 프로필별로 저장 → "나와 비슷한 성향의 사람들이 좋아한 곳" 추천에 반영

### 4.2 상권 주인 기능

**(1) 상권 건강 지표 대시보드**

| 지표 | 산출 방식 (초안) | 데이터 |
|---|---|---|
| 매출 추세 지수 | 업종·지역 카드 소비의 전년 동기·전월 대비 증감, 동일 업종 평균 대비 | D1 |
| 유동 전환율 | 매장 격자 유동인구 대비 소비 건수 | D1, D2 |
| 관광객 유입도 | 외지인·외국인 소비 비중, 내비 목적지 검색량 | D1, D3 |
| 경쟁 밀도 | 반경 300m 동일 업종 점포 수, 최근 개폐업 수 | D5 |
| 접근성 점수 | 정류장·주차장 거리, 주요 관광지와의 이동시간 | D6, D4 |
| 고객 만족 지수 | 앱 평가 평균, 항목별 점수, 리뷰 감성 | 자체 평가 |
| 성향 적합도 | 이 매장을 높게 평가한 관광객 성향 분포 | 자체 평가 |

→ 위 지표를 합친 **종합 "상권 건강 점수" (0~100)** 와 주변 상권 대비 백분위

**(2) AI 상권 컨설팅 리포트**
- 주간 리포트 자동 생성: "평일 17~19시 유동인구는 많지만 전환율이 동일 업종 하위 30%입니다. 이 시간대 방문객은 20대 커플 비중이 높고, 리뷰에서 '좌석이 불편하다'는 언급이 반복됩니다. 해피아워·커플 세트 메뉴를 검토해 보세요."
- 질문형 대화: "왜 지난달 매출이 줄었어?", "어떤 손님을 타겟해야 해?"

**(3) 리뷰 인사이트**
- 리뷰 주제·감성 자동 분류 (맛·가격·친절·분위기·청결·대기)
- 개선이 필요한 항목 순위

### 4.3 순환 구조 (차별점)

1. 관광객 평가 → 상권 "고객 만족·성향 적합도" 지표에 반영
2. 평가 → 성향별 장소 선호도 행렬 갱신 → 다음 코스 추천 품질 향상
3. 사장님이 개선 조치(메뉴·이벤트 등록) → 추천 노출 문구에 반영 → 다시 평가로 효과 측정

## 5. AI Agent 설계

### 5.1 구조

```
                    ┌──────────────────────┐
  사용자 입력 ─────▶│  오케스트레이터 Agent │ (의도 파악, 역할별 Agent 호출)
                    └───┬───────┬───────┬──┘
          ┌─────────────┘       │       └──────────────┐
          ▼                     ▼                      ▼
 ┌─────────────────┐  ┌──────────────────┐  ┌───────────────────┐
 │ 성향 분석 Agent │  │ 코스 플래너 Agent │  │ 상권 분석 Agent    │
 │ 테스트→유형화   │  │ 후보 검색→일정 구성│  │ 지표 계산→원인 분석│
 └─────────────────┘  └──────────────────┘  │ →개선안 리포트     │
                                            └───────────────────┘
          ▲                     ▲                      ▲
          └──────── 공통 도구 (Tool) ───────────────────┘
   sql_query · spatial_search · crowd_forecast · weather · route_time
   review_analyze · score_store · rag_search(장소·업종 설명)
```

### 5.2 Agent별 역할

| Agent | 입력 | 하는 일 | 출력 |
|---|---|---|---|
| 오케스트레이터 | 자연어·화면 이벤트 | 사용자 유형(관광객/상권) 판별, 하위 Agent 호출, 결과 통합 | 최종 답변 |
| 성향 분석 | 테스트 응답, 과거 평가 | 4축 점수 산출, 유형 설명 생성, 선호 태그 추출 | 성향 프로필 |
| 코스 플래너 | 성향, 위치, 시간, 날씨 | 후보 장소 검색 → 점수화 → 이동시간 고려한 순서 최적화 → 추천 이유 생성 | 코스 + 근거 |
| 상권 분석 | 매장 ID, 질문 | 지표 계산 SQL 실행, 비교군 대비 이상치 탐지, 리뷰 요약, 개선안 작성 | 대시보드·리포트 |

### 5.3 추천 점수 (초안)

```
장소점수 = w1·성향적합도 + w2·데이터인기도(D1,D3) + w3·평가점수(자체)
         − w4·혼잡도(D2) − w5·이동시간(D6) + w6·날씨적합도(D7)
```
- 초기에는 가중치 수동 설정, 평가 데이터가 쌓이면 학습으로 조정
- 코스 순서는 이동시간 기준 간단한 TSP(그리디 + 2-opt)로 구성, 식사 시간대 제약 반영

### 5.4 LLM 사용 원칙

- LLM은 **계획·도구 호출·설명 생성**에만 사용하고, 숫자 계산은 SQL·Python 도구가 수행 → 지표 신뢰성 확보, 환각 방지
- 모든 추천·리포트 문장에 근거 데이터(지표명·기간) 표시

## 6. 시스템 구성 (제주시 내 PC 단독 실행)

| 계층 | 기술 (안) | 비고 |
|---|---|---|
| 프론트엔드 | React(Next.js) 웹, 모바일 반응형 (PWA) | 웹/앱 겸용 |
| 지도 | MapLibre + 오프라인 벡터 타일(제주 영역) | 외부 지도 API 미사용 시 데이터 유출 우려 없음. Kakao/Naver 지도 사용 여부는 대회 측 확인 `[확인 필요]` |
| 백엔드 | FastAPI (Python) | Agent·지표 API |
| Agent 프레임워크 | LangGraph 또는 자체 구현 Tool-calling 루프 | |
| LLM | 로컬 오픈 모델 (예: EXAONE, Qwen 계열 7~14B) via Ollama 또는 vLLM | 한국어 성능·PC GPU 사양에 맞춰 선택 `[확인 필요: PC 사양]` |
| DB | PostgreSQL + PostGIS (공간 질의), 집계는 DuckDB | |
| 벡터 DB | Chroma 또는 pgvector | 장소 설명·리뷰 검색 |
| 배포 | Docker Compose 1회 기동 | 인터넷 없이 동작하도록 이미지·모델 사전 포함 |

**데이터 보안 원칙**
- 원천 데이터는 PC 밖으로 나가지 않음 (외부 API 호출 시 원천 데이터 미포함)
- 화면·리포트에는 **집계값만** 표시, 개인 식별 가능한 최소 단위 이하 수치는 마스킹
- 반출 산출물(발표 자료 등)은 센터 반출 규정에 따라 집계 결과만 사용

## 7. 주요 화면 (와이어프레임 수준)

1. **시작 화면**: "여행 왔어요" / "사장님이에요" 선택
2. **성향 테스트**: 카드형 문항 12개 → 결과 유형 카드 (공유 가능)
3. **지도·코스 화면**: 지도 위 코스 경로 + 타임라인, 장소별 "왜 추천?" 펼치기, 대화창으로 수정
4. **평가 화면**: 코스 종료 후 장소별 빠른 평가
5. **사장님 대시보드**: 종합 점수, 지표 카드 7개, 시간대·고객층 차트, 주변 비교 지도
6. **AI 리포트·상담**: 주간 리포트 + 질문 대화창

## 9. 기대 효과

- **관광객**: 검색·후기 비교 시간을 줄이고, 취향과 실제 데이터에 근거한 코스 제공
- **소상공인**: 감이 아닌 객관 지표로 자기 매장 상태를 파악하고, 구체적 개선 방향 확보
- **지역**: 유명 관광지 쏠림 대신 성향 기반으로 골목 상권까지 방문 분산, 평가 데이터라는 새로운 지역 데이터 자산 축적

## 10. 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 카드·유동인구 데이터가 매장 단위가 아닌 격자·업종 단위 | 매장 지표는 "매장이 속한 격자·업종 수준 지표 + 앱 평가"로 정의하고 화면에 단위를 명시 |
| 대회 기간 중 평가 데이터 부족 (콜드스타트) | 데이터 기반 점수로 시작, 시연용 평가는 시뮬레이션 데이터임을 명시 |
| 로컬 LLM 성능·속도 한계 | 계산은 도구가 담당, LLM은 짧은 계획·설명만. 응답 캐시 |
| 데이터 반출 불가로 개발 환경 분리 | 외부에서는 스키마가 같은 가짜(합성) 데이터로 개발, 센터 PC에서 실데이터로 교체 |
| 허위 평가 | 방문 인증, 계정당 하루 평가 횟수 제한 |
