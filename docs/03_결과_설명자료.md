# 03. 결과 설명자료 — 제주잇다 (Jeju-ITDA)

> 관광객의 취향과 제주 상권을 데이터로 잇는 AI Agent 서비스
> 웹(React) · 모바일 앱(Flutter) · Agent 서버(FastAPI) · 제주데이터허브 Open API 11종 연동

## 1. 문제 정의

| 대상 | 지금의 문제 | 제주잇다가 하는 일 |
|---|---|---|
| 관광객 | 후기·검색을 비교하느라 시간이 들고, 유명 관광지만 붐빔. 내 취향·그날 날씨·혼잡을 함께 고려한 코스를 얻기 어려움 | 성향 테스트 → 출발 지역 → **실측 혼잡도·관광지 방문객·실시간 날씨를 반영한 시간표 코스**, 대화로 수정 |
| 상권 주인(소상공인) | 감으로 운영. 손님이 왜 만족·불만인지, 어떤 손님이 오는지 객관적으로 알기 어려움 | 관광객의 **방문 인증 평가**를 근거로 리뷰 주제 분석·개선 제안·질의응답 Agent |
| 지자체 (제주시 Main PC) | 관광 쏠림·상권 상태를 실시간으로 보기 어렵고, 데이터 반출 통제가 필요 | 지역 점수·실시간 이벤트·원천 데이터 적재·품질·접근 통제를 한 콘솔에서, **Agent 지역 보고서** |

**핵심 차별점 — 순환 구조**: 관광객 평가 → 장소 평점·상권 지표·지역 점수 갱신 → 다음 관광객 코스 품질 향상 → 다시 평가.

## 2. Agent 구조

(기획 구성도: `기획/구성도_Agent구조.png`, `기획/구성도_MainPC_데이터아키텍처.png`)

```
 사용자(웹·앱) ──JWT──▶ FastAPI Agent 서버 (/api/v1, Main PC)
                          │
   ┌──────────────────────┼─────────────────────────────┐
   ▼                      ▼                             ▼
 성향 분석 Agent       코스 플래너 Agent              상권·지역 분석 Agent
 · 12문항→4축→16유형    · 장소 점수화(Python)           · 리뷰 주제 분석 (GPT, JSON)
 · 설명 문장 (GPT)      · 대화 수정 / 다른 코스 (GPT)    · 가게 리뷰 보고서 (GPT)
                        · 후보 id 밖 선택 차단           · 사장님 질의응답 (GPT)
                                                       · 지역 점수 + 지역 보고서 (GPT)
   └──────────────────────┬─────────────────────────────┘
                          ▼  공통 도구 (Tool)
   datahub(D2 혼잡도·D4 방문객·버스·와이파이·기상) · weather(기상청/Open-Meteo)
   map(카카오) · photo(네이버) · rating(실제 별점 반영) · geo(거리·이동시간) · SQLite
```

### 설계 원칙 (환각 방지·데이터 보호)
1. **계산은 도구, 설명은 LLM** — 점수·혼잡도·이동시간·지역 점수는 모두 Python 으로 계산하고, GPT 는 고르기·설명·문서 작성만 합니다.
2. **후보 제한** — GPT 는 서버가 넘긴 후보 장소 id 중에서만 고를 수 있고, 목록 밖 id 는 버립니다. 도착 시각·이동 시간은 서버가 다시 계산합니다.
3. **허브 데이터는 등급만 LLM 으로** — 혼잡도 낮음/보통/높음, 인기도 최상위/상위/보통/한산. 원본 행·숫자는 서버(Main PC) 밖으로 보내지 않습니다.
4. **항상 동작** — GPT 키가 없거나 실패하면 규칙 기반 응답·문서로 자동 대체 (응답에 `source: "gpt" | "rule"` 표시). 예외: 사장님 질의응답은 키가 없으면 안내 문구만 돌려줍니다.

### GPT 사용 지점 (8곳)

| Agent | 기능 | 코드 | 출력 |
|---|---|---|---|
| 성향 분석 | 유형 설명 문장 | `services/profile_service.py` | 한 문장 |
| 코스 플래너 | 대화로 코스 고치기 | `services/chat_service.py`, `course_service.edit_course_by_chat` | JSON (reply + stops) |
| 코스 플래너 | 다른 코스 보기 | `course_service.plan_alternative` | JSON (summary + stops/why) |
| 상권 분석 | 리뷰 주제별 반응 | `services/owner_service.py` + `prompts/review_topics.md` | JSON (topic·pos·mentions·summary) |
| 상권 분석 | 가게 리뷰 보고서 | `services/insight_service.py` | 마크다운 |
| 상권 분석 | 사장님 질의응답 | `services/owner_service.py` | 근거 포함 답변 |
| 지역 분석 | 지역 점수 보고서 | `services/insight_service.py` | 마크다운 |
| (웹·앱) | GPT 중계 플래너 | `frontend/src/prompts`, `app/assets/prompts` | 백엔드 중계 API가 있을 때만 사용 (현재 비활성) |

## 3. 주요 기능

### 관광객
- 성향 테스트 12문항 → 16유형 (예: "노을 감성 탐험가")
- 출발 지역 선택 / 현재 위치 → 가장 가까운 지역
- **AI 코스**: 3~5곳 시간표, 장소별 데이터 근거, 실시간 날씨가 비·눈이면 실내 코스
- **대화로 수정**: 해산물·실내·장소 빼기·바다 보이는 카페 등 자유 문장
- **다른 코스 보기**: 이미 본 장소를 피해 새 코스
- 방문 후 별점·한 줄 평 (코스 장소만, 계정당 하루 20건)

### 상권 주인
- 내 가게 연결 (관광객이 평점을 남긴 장소 중 선택)
- 별점·리뷰·손님 성향 분포, 지역 점수
- 리뷰 주제별 반응·리뷰 보고서·AI 질의응답, 메뉴·이벤트 등록
- 새 평가 실시간 알림 (WebSocket)

### 관리자 (Main PC 콘솔)
- 오늘 집계·실시간 이벤트 피드·지역 점수 지도
- 지역 점수 0~10 + Agent 지역 보고서
- 원천 데이터 적재 이력(허브 11종 + 파일), 품질 점검(허위 평가·좌표·쿼터·오류·파일)
- 계정 승인·정지, 접근 기록, 마스킹 규칙, SQLite 백업과 관리자 2인 복구

## 4. 실행 결과 (2026-11-18, 실제 데이터허브·GPT·날씨로 실행)

전체 응답 원문: `docs/실행결과/*.json` (23단계). 실행 스크립트 흐름: 관광객 → 상권 주인 → 관리자.

### 4-1. 데이터허브 실측 혼잡도 (D2, 2026-08-31 기준, 계산 3.0초)
애월읍 지수 1.00 (제주 평균 대비 +111%) · 조천 0.66 (+55%) · 한림·한경 0.25 (−12%) · 서귀포 동지역 0.00 (−53%)

### 4-2. 관광객 — 성향·코스
- 성향: **ANPJ 노을 감성 탐험가** — GPT 설명 "노을을 놓치지 않도록 바다와 전망 좋은 곳을 촘촘히 둘러보는 체험형 여행자입니다." (3.7초)
- 실시간 날씨 (Open-Meteo): 구름 조금 11.0℃, 습도 75%
- 애월읍 출발 코스 (계산 0.1초 미만) — **가장 붐비는 애월(+111%)을 피해 한림으로** 구성

| 시각 | 장소 | 근거 (일부) |
|---|---|---|
| 15:00 | 앤트러사이트 제주 한림점 (카페) | D2 혼잡도 낮음 · 평소보다 12% 한산해요 |
| 16:02 | 협재해수욕장 | D2 혼잡도 낮음 · 평소보다 12% 한산해요 |
| 17:35 | 수월봉 (노을) | D2 혼잡도 낮음 · 평소보다 12% 한산해요 |
| 18:46 | 부두식당 (저녁) | D2 혼잡도 낮음 · 평소 수준이에요 |

- 대화 "카페는 바다 보이는 곳으로 해줘" → *"카페를 바다가 보이는 봄날카페로 바꿨어요. 협재해수욕장과 수월봉, 부두식당은 그대로 유지했어요."* (GPT, 2.8초)
- 대화 "저녁은 회 먹고 싶어" → 이미 방어회 식당(부두식당)이라 유지하고 이유를 설명 (GPT, 4.3초)
- 다른 코스 보기 → *"미디어아트 체험과 한담 산책을 더하고, 곽지해변 노을로 마무리하는 코스예요."* 아르떼뮤지엄 제주 → 한담해안산책로 → 곽지해수욕장 → 애월연어 (GPT, 5.2초, 이전 장소와 겹침 0)

### 4-3. 관광객 평가 → 상권 주인 (순환 구조)
- 부두식당에 평가 5건 저장 (accepted 5 / rejected 0)
- 사장님이 부두식당 연결 → **리뷰 주제별 반응 (GPT, 7.3초)**

| 주제 | 긍정률 | 언급 | 요약 |
|---|---|---|---|
| 맛 | 100% | 3 | 음식 맛에 만족했어요 |
| 주차·접근성 | 0% | 1 | 주차가 불편하다는 의견이 있어요 |
| 친절·서비스 | 100% | 1 | 직원들이 친절하다는 반응이에요 |
| 가격 | 0% | 1 | 가격이 비싸다는 의견이 있어요 |
| 대기 시간 | 0% | 1 | 웨이팅이 길었다는 의견이 있어요 |

- 리뷰 보고서 (GPT, 4.0초) 발췌: *"평균 4.2점으로 음식과 친절도는 호평이지만, 주차·대기·좌석 불편이 보입니다. 리뷰가 5개라 참고 수준으로 봐 주세요."* → 다음 주에 해 볼 일 3가지
- 질의 "평일 저녁 손님을 늘리려면?" (GPT, 6.8초): *"관광객 리뷰가 5건뿐이라 판단에는 한계가 있지만 … 웨이팅 안내와 대기 관리 방안을 점검하고, 홍보에서는 맛과 노을을 함께 강조해 보세요."* — 데이터가 적다는 한계를 스스로 밝힘

### 4-4. 관리자
- 오늘 집계: 방문 인증 5 · 평가 5 · 코스 2
- 지역 점수: 대정·안덕 **8.0** (만족도 7.3, 수요 10.0, 쾌적함 6.8) … 조천 3.8
- **Agent 지역 보고서 (GPT, 9.4초)** 발췌: *"대부분 지역은 최근 7일 리뷰·코스 기록이 없어 지역 간 비교에 한계가 있습니다."* / *"애월읍은 혼잡도 높음에 대응해 혼잡 시간대와 주차·대기 불편을 점검합니다."*
- 적재 이력: 허브 11종 중 10종 수신 이력(내국인 유동인구 688행·버스 이용 5,109행·와이파이 1,270행 등) + 파일 18개

## 5. 검증 방법과 한계

### 5-1. 검증 방법

| 검증 | 방법 | 결과 |
|---|---|---|
| API 계약 | 웹 `client.js`·앱 `client.dart` 가 부르는 경로·요청·응답 형식과 1:1 대조 후 FastAPI TestClient 로 전 흐름 시험 (역할별 권한, 가입 승인, 토큰 갱신·폐기, 오류 형식, WebSocket, 백업·2인 복구) | 62개 항목 통과 (2026-11-16 기준. 이후 바뀐 상권 주인 API 는 아래 23단계 시나리오로 확인) |
| 실데이터 시나리오 | 실제 허브·GPT·날씨로 23단계 실행, 응답 저장 | 23/23 성공 (4장, `docs/실행결과/`) |
| 허브 연동 | 11종 각각 실제 호출: 페이지·재시도·쿼터·캐시·최신 날짜 탐지 | 11종 응답 확인, 날짜별 상시 실패(502) 대응 확인 |
| GPT 안전장치 | 후보 밖 id 차단, JSON 형식 검사, 키 없음·틀림(401)·모델 없음(404)·temperature 미지원 모델 처리 | 실패 시 규칙 기반으로 대체 확인 |
| 제출 zip 재현 | 제출 zip 을 빈 폴더에 풀고 새 가상환경에 `requirements.txt` 설치 → 키 없이(`.env.example` 그대로) 서버 실행 → 관광객 코스·대화·다른 코스·평가 → 상권 주인 가게 연결·리뷰 분석 → 관리자 콘솔 호출 (2026-11-19) | 모두 정상 응답, GPT 기능은 규칙 기반으로 대체 (사장님 질의응답은 안내 문구) |
| 웹 빌드 | `npm run build` | 성공 (JS 300kB / gzip 105kB) |

### 5-2. 한계
- **데이터 시점 지연**: 허브 유동인구는 약 2~3개월 늦음(최신 2026-08-31), 관광지 유입은 2024-12, 허브 기상은 2025-03까지 → "오늘" 혼잡도가 아니라 최근 실측 기준입니다.
- **혼잡도 지수의 단위 편향**: "읍면동당 방문인구"로 비교해 면적이 넓은 읍·면(애월읍 등)이 높게 나오는 경향이 있습니다.
- **파일 데이터 미반영**: 카드 매출·상가·음식점·리뷰 분석 파일 10종은 확보·관리만 하고 점수 계산에는 아직 쓰지 않습니다.
- **추천 후보 37곳**: 직접 정리한 실제 장소 목록이라 범위가 좁습니다.
- **콜드스타트**: 상권 화면·지역 점수는 앱 평가가 쌓여야 의미가 커집니다. 시연 결과도 평가 5건 기준입니다 (Agent 도 이를 스스로 밝힘).
- **외부 LLM**: GPT 는 외부 API 입니다. 허브 원본은 보내지 않도록 설계했지만, 인터넷이 막힌 센터 PC에서는 GPT 기능이 규칙 기반으로 바뀝니다.
- **GPT 없이 실행할 때**: 사장님 질의응답은 동작하지 않고(안내 문구), 리뷰 주제 분석은 키워드 기준이라 정확도가 낮습니다.
- **응답 시간**: GPT 기능은 2~10초 (지역 보고서 9.4초).
- **단일 서버 메모리 상태**: 코스 대화 선호·이벤트 방송은 서버 프로세스 1개 기준.
- **모바일 앱**: Flutter 3.50 이상 필요. 이번 검증 PC(3.47.9)에서는 정적 분석을 실행하지 못했습니다.

## 6. 센터(제주빅데이터센터·제주시 Main PC) 활용 방안

1. **센터 PC 단독 실행** — `docker compose up -d` 로 Agent 서버+웹을 한 대에서 실행. DB(SQLite)·캐시·백업이 모두 `backend/storage/` 안에 있어 반출 통제가 쉽습니다.
2. **센터 반입 데이터 연결** — 카드 소비(D1)·유동인구 원본을 센터에서 받아 `datahub_service` 와 같은 형태의 함수로 붙이면, 상권 매출 추세·유동 대비 전환율이 사장님 화면 지표로 바로 들어갑니다. 코스·지역 점수 코드는 바꿀 필요가 없습니다.
3. **외부 유출 차단** — 허브·센터 원본은 서버 밖으로 나가지 않고, LLM 에는 등급·집계만. 인터넷이 없는 환경에서는 GPT 를 끄고(키 비움) 규칙 기반으로 운영하거나, `llm_service.py` 한 곳만 바꿔 로컬 LLM(예: Ollama·vLLM 의 EXAONE/Qwen)으로 교체할 수 있습니다.
4. **관리 콘솔로 운영** — 원천 데이터 적재 이력·품질 점검·접근 기록·마스킹 규칙·백업(관리자 2인 복구)으로 센터의 데이터 관리 업무에 맞췄습니다.
5. **새 데이터 자산** — 성향별 장소 평가·코스 선택 기록은 기존 공공데이터에 없는 "관광객 만족도" 데이터로, 지역 정책(관광 분산, 골목 상권 지원)의 근거가 됩니다.
