## 3. 전처리 및 분석 흐름

### 3-1. 수집 (허브 API 특성 대응)

실제 호출로 확인한 허브 특성에 맞춰 수집 코드를 만들었습니다.

| 허브 특성 | 처리 |
|---|---|
| 같은 요청도 500/502 가 자주 섞임 | 최대 6회 재시도 (1·2·3…초 간격) |
| 특정 날짜는 계속 실패 | 날짜를 지정하지 않은 요청은 하루씩 앞 날짜로 최대 3번 물러남 |
| 한 번에 최대 100건 (`limit` > 100 이면 5xx) | `number` 로 페이지를 넘기며 전부 수신 |
| 데이터별 하루 1,000회 쿼터 | 호출 수를 파일에 기록, 950회에서 정지 |
| 최신 날짜를 알려 주지 않음 | 지수 탐색 + 이분 탐색으로 "데이터가 있는 가장 최근 날짜" 자동 탐지 (약 10~15회 호출, 12시간 캐시) |
| 지난 날짜 데이터는 바뀌지 않음 | `storage/datahub_cache/` 디스크 캐시 (지난 날짜 영구, 최근 7일·기준정보 24시간, 빈 결과 6시간) |

### 3-2. 지역 혼잡도 지수 (D2 → 코스 추천)

```
유동인구 행(읍면동 × 성별 × 연령, 하루 688행)
  → 읍면동별 방문인구 합계 (visitPop)
  → 서비스 지역 10곳으로 묶기 (REGION_EMD 매핑, 예: 한림·한경 = 한림읍+한경면)
  → 지역별 "읍면동당 방문인구" = 합계 ÷ 읍면동 수
  → 혼잡도 지수 0~1 = (값 − 최소) ÷ (최대 − 최소),  제주 평균 대비 % 함께 계산
```

- **코스 점수**: `장소점수 = 18·성향적합 + 6·데이터근거수 + 14·평점 − 15·혼잡도 + 20·날씨적합 − 1.5·거리(km)`
- **근거 문장**: 장소의 D2 근거를 실측값으로 교체 — 예) "혼잡도 낮음 · 평소보다 12% 한산해요" (2026-08-31 실측)
- 서버 시작 시 백그라운드로 계산, 실패하면 1분 간격 5회 재시도. 계산 전·실패 시 혼잡도 0으로 동작.

실측 결과 (2026-08-31, `docs/실행결과/00_region_crowd_D2.json`)

| 지역 | 혼잡도 지수 | 제주 평균 대비 |
|---|---|---|
| 애월읍 | 1.00 | +111% |
| 조천 | 0.66 | +55% |
| 대정·안덕 | 0.32 | 0% |
| 한림·한경 | 0.25 | −12% |
| 서귀포 동지역 | 0.00 | −53% |

### 3-3. 지역 점수 0~10 (관리 콘솔, `services/insight_service.py`)

```
만족도 50% : 관광객 앱 별점 평균 (리뷰가 적으면 3.5점 쪽으로 당김)
수요   30% : 최근 7일 코스 선택 + 평가 건수 (로그 정규화)
쾌적함 20% : D2 혼잡도 지수 (낮을수록 높음, 없으면 나머지 비중으로 재배분)
```

### 3-4. 장소 평점 (`services/rating.py`)
초기 평점(직접 정리)을 사전 평가 몇 건으로 보고, 관광객 실제 별점이 쌓일수록 실제 평균으로 이동 (베이지안 평균).

### 3-5. LLM(GPT)에 보내는 데이터 원칙
- **숫자 계산은 Python**, GPT 는 설명·대화·문서 작성만 (기획서 5.4절 "LLM 사용 원칙").
- 허브 값은 숫자 대신 **등급만** 전달 (혼잡도: 낮음/보통/높음, 인기도: 최상위/상위/보통/한산).
- 허브 원본 행은 서버(Main PC) 밖으로 보내지 않습니다. GPT 에 가는 것은 앱 자체 평가 텍스트와 집계 점수입니다.

## 9. AI 활용 범위 (대회 규정 명시 사항)

| 구분 | 내용 |
|---|---|
| 서비스에 쓰는 AI 모델 | OpenAI GPT (Chat Completions, 개발·시연 `gpt-6-luna`, `backend/.env` 의 `OPENAI_MODEL` 로 변경). 별도로 학습·미세조정한 모델은 없음 |
